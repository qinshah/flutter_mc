## 渲染异常修复：红色根因 = 提取器把L 模式灰度索引当 RGB（提交 4cb2ce3）

用户报"很多方块渲染成红色"。**排查路径**（可复用）：
① 先验图集本身（越界/尺寸/容量）→ 无问题；② 用 PIL 采样每张贴图主色 →
`grass_block_top` 平均 (147,0,0) 纯红；③ 打印原始 PNG 的 mode 与像素 →
`mode=L`、`(148,148,148)` ⇒ **灰度索引被当 RGB**。

**根因 1（红色）**：`img.Image(width:,height:)` 默认 **uint8/3 通道**，而 jar 里
贴图有 L/P/LA/1 各种模式，`compositeImage`/`setPixel` 是**逐通道**复制 ⇒ L 的灰度
值 v 变成 (v,0,0)。修法：解码后 `convert(numChannels: 4)`，画布与 `_firstFrame`
同改 4 通道。（1076 张 P + 18 张 L + 1 张 1，只有 L 类会出错。）

**根因 2（灰色）**：修完红色才暴露——草方块顶面/云杉叶变灰。L 模式是**索引图**不是
最终颜色，原版运行时用 biome colormap 着色。
- 提取器加`textures/colormap/` 路径（grass/foliage/dry_foliage）。
- **必须乘法不是查表**：判据 `ModelBlockRenderer:215` 是 `multiplyColor(...)`。
  colormap 只有索引 0..127 有值（128 列起纯白），而灰度索引普遍 >127
  （grass_block_top 有 148/195）⇒ 查表直取会拿到纯白（实测草变白）。乘法保留明暗。
- 取默认 biome：判据 `ColorMapColorUtil.get`：`x=(1-temp)*255`、`y=(1-rain*temp)*255`；
  `GrassColor.getDefaultColor()`=`get(0.5,1.0)` ⇒ x=127,y=127。
- **着色对象判据用"内容灰阶检测"**（`decodePng` 已抹掉通道数信息），天然排除自带
  彩色的 P 模式树叶（oak/jungle/birch 调色板是彩色的，本就不该着色）。

结果：grass_block_top (147,0,0)→(71,109,61) 绿、spruce_leaves→(44,84,34) 青绿、
short_grass/fern 上绿、cherry_leaves 保粉、stone/dirt/sand 原样。

**client jar 位置**（下次要重提取时用）：
`~/Library/Application Support/minecraft/versions/26.2/26.2.jar`（含 colormap）。
`~/Desktop/paperMC/*.jar` 是服务端 jar，**不含** assets/minecraft/textures。
另给提取器加了 `restitch` 子命令：从已提取目录重跑图集拼接，**不需 client jar**，
迭代打包策略时省去重解39MB jar。

**蓝色三角斑块（已结）= 树叶全透明**。用户报的"树叶奇奇怪怪 + 蓝色三角"是**同一个
bug 的两个症状**：橡树/桦树叶子彻底消失，只剩树干和后面的天空。

排查关键一步：**直接采样图集里每张贴图的 alpha**（不是只看 RGB）。发现
`oak_leaves`/`birch_leaves` alpha 全是 `0~15`（256/256 全透明）。

**根因 3（树叶透明）**：`oak_leaves` 解码后是 **`Format.uint4`**（只 5 个调色板项）。
`convert(numChannels: 4)` 会把 alpha 按**该格式的位深**解释 —— uint4 下 alpha 上限
就是 15 ⇒ 整张树叶 alpha 变 0~15 ⇒ 渲染时彻底消失。
实测对照：`convert(numChannels:4)`→0~15（错）；`Image.from`→0~255（对）；
手动 `getPixel/setPixelRgba` →0~255（对）。

**最终归一策略（`_toRgba`，两者必须分开处理，写错任一个都会引入新 bug）**：
| 源| 走法 | 理由 |
|---|---|---|
| `numChannels == 1`（L 灰度） | `convert(numChannels:4)` | `getPixel`只填 r，g/b 留 0 ⇒ (v,0,0) 红色；convert 才会把灰度复制到三通道。灰度无 alpha 语义，不受位深影响 |
| `numChannels == 3` | 手动逐像素 + **alpha 补 255** | 无 alpha 通道，`p.a` 不可信；且 uint4 走 convert 会全透明（实测 dirt/sand/oak_log alpha 全 0） |
| `numChannels == 4` | 手动逐像素，`p.a` 直接用 | 走 convert 会按位深截断 alpha |

**教训**：`image` 包的 `convert(numChannels: 4)` **不能当成万能归一化**——它对
低位深格式（uint1/uint2/uint4）的 alpha 解释是错的。凡涉及"贴图变透明/变色"，
先用PIL + Dart 双向打印 `format/numChannels/getPixel` 三元组对齐事实，再动手。

最终验证（三项同时过，缺一不可）：实心方块 alpha 全 255（dirt/sand/oak_log/
birch_log/stone/cobblestone…）、树叶玻璃镂空且 alpha 达 255、全图集"纯灰度残留
(g==0&&b==0)"计数 = 0。

**绕序已实证正确**（别再改）：用纯 Python 对 6 个面 × 4 种索引序算叉积与外法线
点积，当前发射 `2,1,0/3,2,0` **六面全部正面**（dot=+1），`0,1,2/0,2,3` 才是背面。
注意 mesher.dart 原注释写"绕序 0,1,2 / 0,2,3（逆时针为正面）"**与代码不符**，

## jump-height 完成并归档（a0df15a → 7bb8c15，归档 + 主 spec 合并）

**根因是时序顺序**（判据 `LivingEntity.java:2655`
`handleRelativeFrictionAndCalculateMovement`）：
原版每刻**先 `move()` 位移（用未扣重力的vy），再 `travelInAir` 扣重力、再 ×0.98**。
我先前算的"先减重力再位移"给出 0.8322 格（跳不上），原版真实顺序给 **1.2522 格**
（与 Minecraft wiki 跳跃高度一致）。**阻尼模型（×0.98/tick vs exp(-k·dt)）不是根因**，
每子步只差 1e-6。

实现：竖直运动学移到**刻边界（1/20s）推进**（`_vyTicks` 格/刻 + `_verticalTickAccum`），
碰撞仍在 1/120s细步长；每刻 `y += vy` → `vy = (vy - 0.08) × 0.98`。
**关键单位坑**：`gravityPerTick = 0.08`（格/刻²，每刻减 0.08 格/刻），
不是 `32.0/20.0=1.6`——写成 1.6 会让跳高只 0.42 格。

**顺带修掉 4 个连带bug**（都是真机打点/单测暴露的）：
1. **着地闪烁**：`collision.move` 的 `hitY` 只在 `dy<0`（真下沉）时为真，站着不动
   `dy==0` ⇒ 永远撞不到 ⇒ `onGround` true/false 闪。改用 `hasBlockBelow` 探针
   （独立判定，原版 `Entity.groundState` 同义）。
2. **落地速度残留**：`hitY` 时清 `_vyTicks` 与 `velocity.y`，否则站地上vy 恒为
   终端速度 -78.4（注意 `terminalVelocity` 是**负值**、下落口径），每刻"撞停→再被拉下"。
3. **`_jumpedThisTick` 只置 true 不复位** ⇒ 按住空格只能跳一次。真机打点
   （y 升到 57.18 后不动）暴露；改为每刻边界复位。实测 3.3 秒连跳 6 次。
4. **`velocity.y` 暴露滞后**：位移用 `_vyTicks`，但 `velocity.y` 只在

## 飞行逐字翻译（4d650be）

用户纠正"**继续，不能和原版有偏差**" ⇒ 记入用户级 MEMORY：**对齐原版 = 逐字翻译，
不"改进"、不自行解读、不给原版补"合理性"**。

飞行判据（mc-sources/minecraft-26.2）顺序：
`LivingEntity:2656 moveRelative` → `:2658 move` → `:2460/2474 travelInAir`
（扣重力+×0.98）→ `Player:1398 setDeltaMovement(y = originalMovementY × 0.6)`（**覆盖**上面）
→ `:2707 getFlyingSpeed() = getSpeed() × 0.1 = 0.2156 格/刻`。

**我踩的四个坑**（都是"自行发挥"导致的偏差）：
1. 水平写成 `(v + input×accel) × 0.91` ——把**空气阻力**当加速比；判据是**加**，
   且 `getFlyingSpeed()` **不看 isSprinting**（我多加了 ×2 疾跑倍率）。
2. 竖直用 `abilities.flyingSpeed × 3`（0.15）当注入——判据里竖直同样走
   `moveRelative(input × getFlyingSpeed)`，**不读** abilities.flyingSpeed。
3. **收尾多加了 `Math.max`**：判据原文就是 `× 0.6`。解读成 `max(injected, afterGravity)`
   ⇒ 松手时速度锁死在 0.0002 ⇒ **飞行变失重悬浮**（y 卡住不落）。
   这是"感觉变慢"的直接原因。
4. 位移乘了 dt ——原版 `move()` 用 `deltaMovement`（每刻位移），不摊子步。

**判据黄金值（含首帧相位，1 秒 = 120 子步 = 20 刻）**：上升 +0.9443 格、
下降 -0.9443 格（严格对称）、前进 -2.5360 格（yaw=0 朝 −Z）。
"上升/下降不一样"= 第3 点那层多余 `Math.max` 让两条衰减路径不同。

**首帧相位**：我们的 `tick` 首帧先 `accum += dt` 再判跨刻 ⇒ 要攒 6 子步才跨第 1 刻，
故 1 秒实得 19.x 刻而非 20 刻（0.9443 vs 0.9983）。用「相位=0」判据算法可复现
同样的 0.9443 ⇒ 确认是20Hz物理 vs 120Hz 渲染的固有现象，非算法偏差。

## input-focus 实现（487bf06）

用户实机报两个同源现象：玩着玩着**键盘鼠标都失效但 Flutter 按钮仍有动画** +
**按任何键 macOS 都发"无效键盘输入"提示音**。

**判据（`MouseHandler.java`）**：
- `grabMouse()` :404-417 —— 仅 `isWindowActive()` 时抓、抓后指针回中心、置
  `ignoreFirstMove`（:415，避免回中那一下产生视角跳变）、关屏GUI。
- `releaseMouse()` :422-428。
- `cursorEntered()` :430 也置 `ignoreFirstMove`。
- **`RESTORE_KEY_STATE_AFTER_MOUSE_GRAB = !ON_OSX`**（`InputQuirks.java:11`）——
  **macOS 原版抓鼠标时不重置按键**！我原先的 design 判断错了，已在 design.md 修正。
  我们补这一处属**平台差异**（原版 GLFW 在 macOS 上同样丢 KeyUp，靠别的路径兜），
  语义照 `KeyMapping.releaseAll()`（`KeyMapping.java:57`）：把键视为**松开**而非忽略。

**实现**：`KeyMap.releaseAll()`；`_GameScreenState with WidgetsBindingObserver`
（`didChangeAppLifecycleState` 非resumed 即清键 + 重算意图 + **同步全松开上行**）
；游戏区 `Listener(translucent)` 点击即 `requestFocus` 并**首次点击进入捕获**；
指针捕获用**原生近似**（零新依赖）：`onPointerHover` 检出贴边/越界 ⇒ 回中+忽略该次
移动，`_handlePointerMove` 贴边时把位移反向减掉防"粘住"；`Esc` 解除。

**踩坑**：Flutter 的 `Listener` **没有 `onPointerExit`**（那是 `MouseRegion` 的）。
改用"`onPointerMove` 停滞 + `onPointerHover` 恢复"判据越界。另`Offset` 用 `.dx/.dy`
不是 `.x/.y`；`Vector2` 没有 `subtract`/`abs`，且 `InputState.lookDelta` 是 final
只能用 `sub()`。

**测试**：`key_map_test.dart` +2 项；全仓 **56 项全绿**，analyze 零 issue。
真机日志证实：`[KEY] 进入指针捕获` → `[KEY] 忽略回中那一次移动` → 键盘仍可用。

## ⚠️ 键盘提示音的真根因在 Flutter 框架（18552f9）

用户反馈"声音还在"⇒ 说明 `releaseAll` 只解决了一半。**真根因**在
`flutter/lib/src/widgets/keyboard_listener.dart:71-78`：

    onKeyEvent: (FocusNode node, KeyEvent event) {
      onKeyEvent?.call(event);
      return KeyEventResult.ignored;      // ← 无条件 ignored
    },

`KeyEventResult.ignored` 的文档（`focus_manager.dart:78-80`）明说事件
"should continue to be propagated to other key event handlers,
**even non-Flutter ones**" ⇒ **每个按键都漏回 macOS ⇒ 系统 beep**。

**关键**：`KeyboardListener.onKeyEvent` 签名是 `void` ⇒ **无法表达"已处理"**，
所以此前无论 `_onKey` 写什么都必然被系统看到。

**修法**：改用 `Focus`（`onKeyEvent` 返回 `KeyEventResult`）+ 返回 `handled`。
判据 `KeyMapping.click/set`（`KeyMapping.java:30/34`）走 GLFW 回调、独占消费不
回灌系统 ⇒ 原版无此beep。保留例外：`Esc` 配 Ctrl/Meta 交回平台（macOS 退全屏）。

**教训**：报"系统 beep / 键鼠失效"这类**跨边界症状**时，别只看自己的逻辑 ——
往上查框架那一层的返回值语义。这次翻了 Flutter 源码才定位。

**同源但不同触发路径**（我一度混为一个）：
- 按键卡住/一直前进 ⇒ 失焦丢 KeyUp ⇒ `releaseAll` 治
- 系统提示音 ⇒即使聚焦也响 ⇒ `KeyboardListener` 冒泡 ⇒ `Focus`+handled 治
